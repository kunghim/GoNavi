# GoNavi Issue 提交

将扫描发现转成可维护、可复现、可验收的 GitHub Issue。默认目标仓库是 `Syngnat/GoNavi`；当前工作树的 `origin` 可能是个人 fork，不能据此猜测 Issue 目标。

## 安全边界

- 只有用户明确确认提交时，才执行 `scripts/submit_issue.ps1 -Confirm`。
- 未确认时只生成草稿或执行 `-DryRun`，不得调用创建接口。
- 正文和命令中不得出现密码、Token、完整连接串、私钥或未经脱敏的业务数据。
- 提交失败或回读校验失败时，不得标记为已提交。

## 工作流

1. 读取指定报告和发现 ID；没有指定时让用户选择一个候选，不替用户批量提交。
2. 判断类型：Bug 使用 `bug` 标签，需求使用 `enhancement` 标签。所有由本 skill 提交的 Issue 额外使用 `gonavi-scan` 标签；不创建验证状态标签。
3. 保留发现原有验证状态：`已验证`、`代码证据未运行时验证` 或 `待验证`。验证状态写在正文，不得把未验证推断写成已复现。
4. 查重：使用目标仓库的 `gh issue list --state all --search`，同时检查发现 ID、功能名和关键结论。
5. 生成正文。Bug 至少包含：来源与发现 ID、验证状态、环境、前置条件、最小复现步骤、期望行为、实际行为、代码/测试证据、影响、建议验收标准和验证边界。需求至少包含：目标用户、场景、现状痛点、期望流程、验收标准和兼容性影响。
6. 先以 `-DryRun` 检查标题、类型、标签和正文完整性，向用户展示草稿；获得明确确认后再加 `-Confirm` 执行。
7. 创建成功后立即用 `gh issue view` 回读 `number`、`title`、`state`、`labels` 和正文标记；仅当目标仓库、标题、类型标签和 `gonavi-scan` 标签均匹配时报告成功。
8. 将 Issue URL、编号和状态回写到对应扫描报告；不得修改业务代码。

## 草稿约定

标题应描述用户可观察的问题，避免把实现猜测写进标题，例如：`[Bug] SQL Server DDL 查看返回占位注释但显示成功`。

正文末尾保留简短来源标记：

```md
---
来源：gonavi-scan
发现 ID：FIND-...
提交方式：AI 辅助整理，人工确认后提交
验证状态：已验证 / 代码证据未运行时验证 / 待验证
```

验证状态不影响人工确认后的提交资格，但必须决定正文措辞和复现路径的强度。

## 提交脚本

使用 [scripts/submit_issue.ps1](scripts/submit_issue.ps1)。默认只做预检和草稿检查；只有显式传入 `-Confirm` 才会创建 Issue。脚本默认提交到 `Syngnat/GoNavi`，需要其他目标时必须显式传入 `-Repo`。
