### FIND-SYNC-001 差异同步不支持复合主键表

- 类型：产品缺口。
- 严重度：P2。
- 置信度：高。
- 验证状态：已验证（代码与自动化测试）。
- 关联能力：`CAP-SYNC-001`。
- 结论：表到表和 SQL 结果到表的差异同步只支持单列主键；无主键或复合主键会被拒绝或跳过。因此，以复合主键建模的业务表无法使用差异预览与增量同步闭环。
- 证据：`internal/sync/analyze.go:191`、`internal/sync/preview.go:103`、`internal/sync/source_query_sync.go:82`、`internal/sync/sync_engine.go:326`。
- 测试证据：`internal/sync/analyze_i18n_test.go:294`、`preview_i18n_test.go:188`、`source_query_sync_test.go:262` 明确断言复合主键错误路径。
- 影响：使用联合业务键的表只能改用直接导入、调整表结构或通过其他方式同步，无法获得差异对比能力。

验证路径：

1. 准备源表和目标表，均使用两个字段组成复合主键，例如 `PRIMARY KEY (tenant_id, user_id)`。
2. 在数据同步工作台选择差异同步或差异预览。
3. 选择上述源表与目标表并执行分析。
4. 预期结果：系统能够用两个主键字段唯一定位行，生成新增、更新和删除差异。
5. 实际结果：后端返回“复合主键当前暂不支持差异同步/预览”的错误或跳过该表。
6. 自动验证命令：

```powershell
go test ./internal/sync -run "TestAnalyzeUsesCurrentLanguageForReadAndPKMessages|TestPreviewUsesCurrentLanguageForPreflightErrors|TestResolveSinglePKColumnUsesCurrentLanguageForQueryDiffErrors" -count=1
```

本次执行结果：`PASS`，`ok GoNavi-Wails/internal/sync 5.564s`。

建议：将复合主键值建模为有序元组，并统一扩展分页、反查、差异集合和行选择逻辑；验收需覆盖 MySQL-like、PostgreSQL-like 和可选 Driver Agent 路径。

### FIND-SYNC-002 TDengine 和 IoTDB 目标无法应用更新与删除差异

- 类型：产品能力缺口。
- 严重度：P2。
- 置信度：高。
- 验证状态：已验证（自动化测试）。
- 关联能力：`CAP-SYNC-A03`、`CAP-DS-TDENGINE`、`CAP-DS-IOTDB`。
- 结论：同步目标为 TDengine 或 IoTDB 时，`ApplyChanges` 仅接受新增行；只要变更集合包含 UPDATE 或 DELETE 就拒绝执行。因此时序目标只能做追加式迁移，不能完成通用差异同步闭环。
- 证据：`internal/db/tdengine_impl.go:432`、`internal/db/iotdb_impl.go:420`、`internal/sync/schema_migration_test.go:886` 和 `:923`。
- 影响：用户若把“差异同步”理解为源目标一致，目标端旧记录修改或删除将无法落地；系统虽会警告/拒绝，但任务目标不能完成。
- 建议：在选择目标和同步模式时提前将能力矩阵展示为“仅追加”；后续若实现变更语义，应分别按时间戳/设备主键设计 TDengine 与 IoTDB 的更新删除策略。

验证路径：

1. 准备一张源表和一个含对应历史记录的 TDengine 或 IoTDB 目标。
2. 让源记录发生更新或删除，进入数据同步并选择差异模式。
3. 预期结果：若产品承诺差异同步，应能把更新/删除应用到目标；若只支持追加，应在分析阶段禁用该模式并明确解释。
4. 实际结果：迁移计划给出仅 INSERT 警告，`ApplyChanges` 拒绝含更新/删除的集合且不会部分写入。
5. 本次执行：

```powershell
go test -tags gonavi_tdengine_driver ./internal/db -run "TestTDengineApplyChanges_RejectsMixedUpdatesWithoutPartialWrite" -count=1 -v
go test -tags gonavi_iotdb_driver ./internal/db -run "TestIoTDBApplyChangesBuildsInsertAndRejectsMutatingDiffs" -count=1 -v
go test ./internal/sync -run "TestBuildSchemaMigrationPlan_TDengineTargetWarnsInsertOnlyBoundary|TestBuildSchemaMigrationPlan_IoTDBTargetWarnsInsertOnlyBoundary" -count=1 -v
```

本次结果：三组测试均 `PASS`；TDengine 与 IoTDB 驱动测试分别使用对应 build tag，确认测试确实执行。

### FIND-SYNC-003 结构同步不会迁移前缀索引和部分索引类型

- 类型：产品能力缺口 / 性能风险。
- 严重度：P2。
- 置信度：高。
- 验证状态：已验证（自动化测试）。
- 关联能力：`CAP-SYNC-A07`。
- 结论：结构迁移遇到 MySQL 前缀索引或 FULLTEXT 等未支持索引类型时，会把它们登记为 unsupported，而不会在目标创建等价索引。
- 证据：`internal/sync/schema_migration.go:339`、`:344` 及其他方言 planner 的对应分支；`internal/sync/schema_migration_test.go:142`。
- 影响：数据可以迁移成功，但依赖前缀或全文索引的查询性能、检索行为和运维预期不会随结构一起迁移；若用户只关注任务成功状态，容易遗漏后续人工补建。
- 建议：结果页把“未迁移对象”提升为独立验收清单并支持导出/复制补救 DDL；对可等价映射的目标生成方言化索引。

验证路径：

1. 在源 MySQL 表创建 `KEY idx_name_prefix(name(16))` 和 `FULLTEXT KEY idx_note(note)`。
2. 选择支持结构同步的源/目标组合并执行分析。
3. 观察结构计划的 unsupported 列表，并在完成后检查目标索引。
4. 预期结果：等价索引被创建，或任务完成前要求用户明确处理。
5. 实际结果：两类索引进入 unsupported 警告，不生成迁移 SQL。
6. 本次执行：

```powershell
go test ./internal/sync -run "TestBuildSchemaMigrationPlan_AutoCreateWhenTargetMissing" -count=1 -v
```

本次结果：`PASS`，测试明确断言前缀索引和 FULLTEXT 索引位于 unsupported 列表。

### FIND-MSG-001 查看消息型数据源字段会实际读取样本消息

- 类型：运维风险 / 产品交互缺口。
- 严重度：P2。
- 置信度：高。
- 验证状态：已验证（代码路径与自动化测试）。
- 关联能力：`CAP-ROCKET-A06`、`CAP-MQTT-A05`、`CAP-KAFKA-A06`、`CAP-RABBIT-A05`。
- 结论：Kafka、MQTT、RocketMQ 和 RabbitMQ 的 `GetColumns` 不是只读静态 Schema，而会读取最多 20 条实际消息以推断 Payload 动态字段。MQTT 会临时订阅等待消息；RabbitMQ 使用 `ack_requeue_true` 取样后重入队。
- 证据：`internal/db/kafka_impl.go:330`、`mqtt_impl.go:332`、`rocketmq_impl.go:377`、`rabbitmq_impl.go:383` 和 `:821-833`。
- 影响：用户只是打开字段元数据或触发全库字段搜索，也可能产生最长约 10 秒等待、Broker 读取/订阅活动、额外权限要求，以及 RabbitMQ 的 redelivered 标志或顺序扰动。
- 建议：默认只显示静态消息元字段；把 Payload 推断改成显式“读取样本”动作，执行前说明副作用，并提供禁用、限时、样本量和缓存策略。

验证路径：

1. 准备四类消息数据源，其中 RabbitMQ Queue 含有顺序可辨识的消息。
2. 不执行消费查询，只打开 Topic/Queue 的字段元数据或在全库搜索中触发列加载。
3. 预期结果：纯元数据操作不应产生消费、订阅、重投递或明显等待；若必须抽样，应先征得用户确认。
4. 需观察信号：Kafka/RocketMQ 的 fetch 请求、MQTT 临时订阅、RabbitMQ `/api/queues/.../get` 请求、消息 `redelivered` 标记与前后顺序。
5. 本次执行：

```powershell
go test ./internal/db -run "TestKafkaGetColumnsIncludesDerivedFields|TestMQTTQueryExecAndColumns|TestRocketMQQueryExecAndColumns|TestRabbitMQQueryExecAndColumns|TestRabbitMQConnectRejectsAMQPPortsBeforeDial" -count=1 -v
```

本次结果：5 项测试全部 `PASS`，耗时 3.734s；真实 Broker 的顺序和订阅副作用仍需按上述路径观测。

### FIND-SQLSERVER-001 SQL Server DDL 查看返回成功但内容只是占位注释

- 类型：功能 Bug。
- 严重度：P2。
- 置信度：高。
- 验证状态：待验证（缺少真实 SQL Server/Driver Agent 运行环境）。
- 关联能力：`CAP-DATA-A09`、`CAP-DS-SQLSERVER`。
- 结论：`SqlServerDB.GetCreateStatement` 不查询真实表定义，而是返回 `SHOW CREATE TABLE not supported...` 注释，同时 error 为 nil。上层可能把它当成成功 DDL，导致 DDL 视图或依赖该接口的导出流程展示/产出不可执行内容。
- 证据：`internal/db/sqlserver_impl.go:532-533`；上层入口 `DBShowCreateTable`、`DataGridV2DdlWorkspace.tsx`。
- 影响：SQL Server 用户不能从 GoNavi 获取可复建表结构，且“成功”状态掩盖了能力缺失。
- 建议：用 `sys.tables/sys.columns/sys.indexes/sys.foreign_keys` 组装定义，或在未实现前返回结构化 unsupported 错误并让 UI 明确禁用 DDL/结构导出。

验证路径：

1. 安装并启用 SQL Server Driver Agent，连接一个包含主键、默认值和索引的测试表。
2. 在表数据页切换到 DDL 视图，或从对象菜单请求表结构。
3. 预期结果：显示可执行的 `CREATE TABLE` 及必要约束/索引。
4. 需观察信号：当前实现预计返回两行注释且操作被视为成功；确认 UI 是否误显示为完整 DDL，以及 SQL 导出是否复用此结果。

### FIND-ROCKETMQ-001 RocketMQ 无法通过 SSH、代理或 HTTP 隧道接入隔离网络

- 类型：产品能力缺口。
- 严重度：P2。
- 置信度：高。
- 验证状态：待验证（缺少真实 RocketMQ 与跳板网络）。
- 关联能力：`CAP-CONN-A08`、`CAP-CONN-A10`、`CAP-DS-ROCKETMQ`。
- 结论：RocketMQ 连接代码在建立运行时前直接拒绝 `UseSSH`、`UseProxy` 和 `UseHTTPTunnel`，只能要求客户端直连 NameServer 与 Broker。
- 证据：`internal/db/rocketmq_impl.go:136-145`。
- 影响：企业内网、堡垒机和跨网段场景无法复用 GoNavi 已有网络安全能力；即使 NameServer 可达，Broker 返回地址也可能对客户端不可达。
- 建议：支持 NameServer 和 Broker 地址的统一隧道/代理解析，并增加 Broker 地址重写或映射配置。

验证路径：

1. 部署只允许经 SSH 跳板访问的 RocketMQ，客户端不能直连 NameServer/Broker。
2. 新建 RocketMQ 连接并启用 SSH 隧道，填写有效跳板信息后测试。
3. 预期结果：隧道建立后可发现 Topic 并访问 Broker。
4. 需观察信号：当前代码预计在网络拨号前返回“暂不支持 SSH 隧道”；代理或 HTTP 隧道路径同样应被拒绝。

### FIND-MONGODB-001 MongoDB SRV 连接不能使用 SSH 隧道

- 类型：产品能力缺口。
- 严重度：P3。
- 置信度：高。
- 验证状态：待验证（缺少 SRV DNS 与跳板环境）。
- 关联能力：`CAP-CONN-A08`、`CAP-DS-MONGODB`。
- 结论：使用 `mongodb+srv://` 时，MongoDB 驱动明确拒绝 SSH 隧道；普通种子地址与 SRV 模式的网络能力不一致。
- 证据：`internal/db/mongodb_impl.go:340`、`mongodb_impl_v1.go:341`。
- 影响：采用 Atlas 风格 SRV 记录但必须经堡垒机访问的用户，需要手工解析并维护成员地址，连接体验和容灾能力下降。
- 建议：解析 SRV/TXT 记录后为每个成员建立可复用转发，并处理副本集返回地址映射。

验证路径：

1. 准备只能经 SSH 跳板访问的 MongoDB 副本集和可解析的 SRV 记录。
2. 使用 `mongodb+srv://` 创建连接并打开 SSH。
3. 预期结果：解析 SRV 后通过隧道连接并发现副本集成员。
4. 需观察信号：当前实现预计在连接前返回“SRV 记录模式暂不支持 SSH 隧道”；对照普通 `mongodb://host` 路径确认差异。

### FIND-MQTT-001 MQTT 通过代理时不支持 WebSocket 传输

- 类型：产品能力缺口。
- 严重度：P3。
- 置信度：高。
- 验证状态：待验证（缺少 MQTT WebSocket 与代理环境）。
- 关联能力：`CAP-CONN-A10`、`CAP-DS-MQTT`。
- 结论：MQTT 的代理路径只支持 tcp/ssl，WebSocket 连接在启用代理时被明确拒绝。
- 证据：`internal/db/mqtt_impl.go:748`。
- 影响：只开放 WebSocket 入口、同时要求经企业代理访问的 Broker 无法接入；这在浏览器友好或防火墙限制环境中较常见。
- 建议：为 ws/wss 接入代理拨号器并覆盖 HTTP CONNECT、TLS SNI 和认证。

验证路径：

1. 启动仅暴露 wss 的 MQTT Broker，并配置必须经过的 HTTP/SOCKS 代理。
2. 新建 MQTT 连接，选择 WebSocket 地址并启用代理。
3. 预期结果：代理完成 WebSocket 握手后可订阅和发布。
4. 需观察信号：当前实现预计返回“不支持通过代理建立 WebSocket 连接”；改用 tcp/ssl 后同一代理配置应进入后续连接阶段。
