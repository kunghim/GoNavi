# GoNavi Issue 处理规范

本规范是 `TASK_WORKFLOW.md` 的补充，只回答一个问题：**从接到 Issue 到产出可提 PR 的代码，中间应该怎么走、什么时候提交、什么时候审查。**

分支创建、远程同步、个人资料边界、PR 授权等仍以 `TASK_WORKFLOW.md` 为准，本文不重复定义。
配套文件：`.claude/PR_TEMPLATE.md`（PR 标题与正文模板）。

---

## 零、第一原则：成本必须匹配收益

本条优先级最高，用于否决本文其余条款的机械执行。

**目标：本可以十分钟做完的修复，不应该花两小时。** 流程是为了降低返工，不是为了证明工作量。任何一步如果对当前任务不产生新的判断依据，就跳过。

### 0.1 任务分级

动手前先分级，分级决定后续流程强度：

| 级别 | 判断标准 | 实现方式 | 提交次数 | 子 Agent 审查 |
| --- | --- | --- | --- | --- |
| **L0 微任务** | 单点改动，1-3 个文件，行为明确无歧义（文案、typo、单行逻辑、补一条测试） | 直接改 | 1 次 | 1 轮，轻量 |
| **L1 常规任务** | 局限在单一模块，改动可一次验证 | 直接改 | 1 次 | 1 轮，完整 |
| **L2 复杂任务** | 跨模块、涉及接口/协议/存储/构建链路，或需求边界不清 | 分阶段 | 每阶段 1 次 | 每阶段 1 轮 + 修复后复审 |

判不准时按低一级处理，并在汇报中说明；确实需要升级时再升级，不要预防性升级。

### 0.2 审查轮次上限

| 级别 | 上限 |
| --- | --- |
| L0 | 1 轮 |
| L1 | 2 轮 |
| L2 | 3 轮 |

达到上限仍未收敛时，停止循环，向用户汇报「已修复项 / 未修复项 / 争议项」，由用户决定是否继续。**不得自行继续加轮次。**

### 0.3 效率红线（违反即为流程失败）

- 不为局部修复默认执行 `go test ./...` 或前端全量测试；测试分层见 `TESTING.md`。
- 不对 L0 任务启动多视角全仓扫描或大范围代码考古。
- 不在没有新证据（新测试、新复现、新 diff）的情况下重复审查同一问题。
- 不把审查者的每一条建议都当作待办。
- 不为「可能将来会用到」而扩大改动范围。
- 不在单个阶段里塞入多个不相关目标。

## 一、第一步：分析定位并汇报（动手前）

接到 Issue 后**先不改代码**，完成以下四步，然后输出汇报。

### 1.1 复现

- 在最新 `upstream/dev` 上复现（分支创建见 `TASK_WORKFLOW.md` 三）。
- 记录：复现步骤、实际结果、期望结果、环境。
- 无法复现时如实记录证据并停止，**不得为了能提 PR 而猜测性改代码**。

### 1.2 定位

- 按 `MODULE_INDEX.md` 找到模块，先读目标文件与其测试，再搜调用方。
- 定位到具体文件与行为，不停留在「某模块有问题」。
- 区分**根因**、症状、以及顺带发现的既有问题。既有问题单独记录，不混入本次修复。

### 1.3 影响面

- 该行为被谁依赖，改动会波及哪些路径。
- 是否存在安全、只读策略、数据兼容、Wails 方法签名或 `QueryResult` 契约风险。

### 1.4 汇报（必须）

```markdown
## Issue 分析
- Issue： #N / 链接
- 级别： L0 / L1 / L2
- 现象： …
- 根因： <文件:行> …
- 影响面： …
- 修复方案： …
- 阶段拆分（仅 L2）： 阶段 1 … / 阶段 2 …
- 验证计划： <定向测试命令>
- 需要用户决策： 有 / 无（内容）
```

汇报后的推进规则：

- **L0 / L1**：用户确认或未提出异议即可开工；若用户已明确说「直接做」，可省略等待。
- **L2**：必须等用户确认阶段拆分后再动手。

## 二、执行：小任务直接做，复杂需求分阶段

### 2.1 小任务（L0 / L1）

一次做完：改代码 → 跑定向测试 → 自查 diff → 提交 → 子 Agent 审查 → 主 Agent 判断 → 修复并提交 → 复审（如需）→ 收尾。

不要为了「看起来规范」把 L0 拆成多个阶段。

### 2.2 复杂需求（L2）

拆成**可独立验证、可独立提交**的阶段。每个阶段必须满足：

- 阶段结束时仓库处于可编译、可过测试的状态。
- 只围绕一个目标，不混入下一阶段内容。
- 顺序优先「先立契约再改实现」「先补测试再改行为」。

每个阶段重复以下循环：

```text
实现阶段目标
  → 定向测试 + 自查 diff
  → 提交（中文）
  → 子 Agent 审查
  → 主 Agent 判断（见 五）
  → 有 A 类问题： 修复 → 提交 → 复审（只复审修复点）
  → 该阶段收敛： 进入下一阶段
```

阶段计划发生实质变化时（范围扩大、发现新根因、需要改接口），先向用户汇报再继续。

## 三、提交：每个可验证单元一次

### 3.1 提交时机

- **每次处理完成后提交一次**，即每完成一个可独立验证的改动单元就提交。
- L0 / L1：一次改动对应一次提交。
- L2：每个阶段一次提交；该阶段内的每次修复再各自提交。
- **修复不 amend 原提交**，独立成提交，便于审查者对比「原改动 → 修复」。

### 3.2 提交信息必须中文

格式沿用仓库规范：

```text
emoji type(scope): 中文描述
```

示例：

```text
🐛 fix(query-editor): 修复 CTE SQL 被误判为高风险
✅ test(data-sync): 补充调度立即运行的审批凭证用例
🐛 fix(data-sync): 修复立即运行后凭证重复审批
```

要求：

- 描述部分**必须中文**，禁止英文句子、拼音、无意义缩写。
- `type` / `scope` 可保留英文：`fix`、`feat`、`test`、`refactor`、`chore` 等；scope 用模块名。
- 一条提交只对应一个目标；修复提交写明修的是什么。

### 3.3 提交前自检

```powershell
git status --short
git diff --stat
git diff --check
git diff --cached --name-status
git diff --cached --check
```

必须确认暂存区不含：

- `AGENTS.md`、`CLAUDE.md`、`.claude/`、`.agents/` 等个人辅助内容
- 密钥、连接串、隐私数据、调试输出、临时文件
- 与本次目标无关的改动或格式化

### 3.4 授权边界

用户在本任务中授权提交后，可对**本任务分支**按上述粒度正常 `git commit`。

`git push` 与创建/更新 PR 仍需单独明确授权，见 `TASK_WORKFLOW.md` 七与 `PR_TEMPLATE.md` 六。

## 四、子 Agent 审查

### 4.1 触发时机

每次提交后立即启动，不攒批。L2 每个阶段各启动一次。

### 4.2 交给审查者的输入

- Issue 原文或编号与验收要求
- 本次改动范围：`git diff <base>...HEAD`、`git log --oneline <base>..HEAD`
- 已执行的测试与结果
- 明确的边界声明：**只看本次改动引入的问题，不做全仓审计**

不要只丢一句「审查一下」，也不要把无关上下文塞进去。

### 4.3 审查方向

必查三项：

1. **问题是否真正解决**：对照复现步骤与验收要求，确认根因被消除，而不只是现象消失。
2. **是否仍有遗留问题**：同一根因的其他触发路径、边界条件、错误分支、并发与取消、空值与异常输入。
3. **是否引入其他功能问题**：调用方回归、接口与 JSON 契约兼容、平台差异、i18n 文案同步、性能与资源释放。

按改动类型追加：

- 前端：多语言是否同步、状态与副作用、重渲染、既有测试是否被削弱。
- 后端 / 驱动：`context` 传递、错误包装、连接与游标释放、方言兼容。
- 数据 / 存储：迁移兼容、并发写、原子性。
- 构建 / 发布：跨平台、CI 兼容、签名与打包。

### 4.4 审查输出必须结构化

```markdown
## 结论
已解决 / 部分解决 / 未解决

## 问题清单
1. [严重度： 高 / 中 / 低] 描述
   - 证据： <文件:行> / <复现步骤> / <失败用例>
   - 类型： 本次引入 / 既有问题 / 推测
   - 建议： …

## 回归风险
…
```

**每条问题必须给出证据。** 只能给出「可能」「建议考虑」的条目必须标注为推测，这些条目默认不进入修复清单。

## 五、主 Agent 判断（Triage）

审查结果是**输入**，不是命令。主 Agent 必须逐条判断并承担判断责任。

### 5.1 三类分流

| 类别 | 定义 | 处理 |
| --- | --- | --- |
| **A 必收** | 确实由本次改动引起；或本次问题未被真正解决；或触碰安全、只读策略、数据兼容、公共契约等硬约束 | 立即修复并提交 |
| **B 记录** | 真实存在，但属于既有问题或超出本次 Issue 范围 | 不修；收尾汇报中列出，必要时建议另开 Issue |
| **C 驳回** | 推测性、无证据、过度防御；风格偏好；要求顺带重构；要求覆盖无关路径；对未改动代码的泛化担忧 | 不修，不展开讨论 |

### 5.2 判定依据

按顺序看：

1. **有无证据**：能给出具体失败用例、复现步骤或 `文件:行` 的倾向 A；只有猜测的倾向 C。
2. **是否本次引入**：用 `git diff <base>...HEAD` 判断；改动范围外的既有问题归 B。
3. **是否在本次 Issue 范围**：超出验收要求的归 B，即使结论正确。
4. **是否触碰硬约束**：安全、数据、契约问题的门槛放低，即使证据偏弱也倾向 A。
5. **修复成本**：需要大范围重构才能解决的，不在本 Issue 内顺手做，归 B。

### 5.3 判断必须显式输出

```markdown
## 审查判断
- A 必收： <条目> → <修复方案>
- B 记录： <条目> → 建议另开 Issue / 后续处理
- C 驳回： <条目> → 理由（推测 / 既有 / 超范围 / 无证据）
```

禁止两种极端：

- **全盘接收**：把审查者所有建议都做成待办，导致范围膨胀、时间与 token 大量消耗。
- **全盘驳回**：以「审查过度担忧」为由跳过真实问题，尤其是回归与硬约束问题。

## 六、修复与复审循环

### 6.1 流程

```text
修复 A 类问题
  → 跑定向测试（覆盖被修的那一点）
  → 提交（中文，写明修了什么）
  → 子 Agent 复审
  → 仅针对修复点确认是否收敛
  → 仍有 A 类： 回到「修复」
  → 无 A 类： 收敛，进入下一阶段或收尾
```

### 6.2 复审范围必须收敛

复审只覆盖：

- 上一轮 A 类问题的修复点
- 该修复直接触及的调用方

**不要重新发起全量审查。** 每轮全量审查是成本失控的主要原因。

### 6.3 停止条件

满足任一即停止循环：

- 无 A 类问题。
- 达到级别对应的轮次上限（见 0.2）。
- 连续两轮审查未提出新的 A 类问题。

触发上限或认为审查者陷入重复拉锯时，向用户汇报并请示，不要自行继续。

### 6.4 需要升级给用户的情况

- 需要扩大改动范围或改动公共接口
- A 类与 B 类难以判定
- 复现依赖不可控外部环境
- 审查结论互相矛盾且无法用证据裁决

---

## 七、收尾

处理完成后向用户汇报：

```markdown
## 处理结果
- 根因与修复： …
- 提交： <hash> <中文提交信息> …
- 验证： <实际执行的测试与结果>
- 审查： 轮次 N；A 已修 M 项；B 记录 K 项；C 驳回 J 项
- B 类遗留（不在本次范围）： …
- 待人工验证： <UI 或交互项的验证入口>
```

收尾后：

- 不要自动 `push`，不要自动创建 PR；等用户明确授权（`TASK_WORKFLOW.md` 七）。
- 需要发 PR 时，按 `.claude/PR_TEMPLATE.md` 组织标题与正文。
