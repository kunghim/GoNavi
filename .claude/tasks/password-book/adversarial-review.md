# GoNavi 密码本需求与技术方案：对抗性审查报告

- 审查日期：2026-10-05。
- 范围：requirements.md、technical-design.md v1.0；现有相关仓库代码与官方资料。
- 方式：3 个子 agent 分别审查加密/生命周期、入口/明文/网络、跨平台/结构兼容；主 agent 核对、去重和调整优先级。
- 约束：不修改原需求、技术策略或代码，不构建/安装依赖，不调用真实凭据，不修改远程状态。本报告单独保存，不自动采纳任何建议。
- 性质：设计审查，不是渗透测试、实现验收或安全认证。以下“高/中”是落实优先级，不代表尚未实现的密码本已经存在对应漏洞。
- 阅读顺序：第 1—8 节保留原审查记录；后续讨论后的优先级与验证范围以第 9 节为准，不将原审查建议自动变成首版要求。

## 1. 结论

没有找到必须推翻 SQLCipher、每本独立密钥、系统保管免主密码、官方定义外置、完整历史或原生桌面搜索策略的证据。现有设计方向可继续，但不能据本轮只读审查声称已经安全验证通过。

去重后保留 3 项高优先级缺口、7 项中优先级细化问题、1 项后续格式兼容提醒；另外明确 2 项已在方案中承认的依赖/发布门槛。

建议均可以在保留原策略的前提下处理。未据本报告修改需求或技术方案；具体建议仍等待后续讨论和工程验证。

## 3. 高优先级发现

### R01. 自动数据库验证的传输安全与服务器身份

位置：技术方案 278、282 行；需求 271 行。

场景：用户保存远程 PostgreSQL 信息，立即自动测试。若新适配器直接使用现有 ConnectionConfig 零值，UseSSL=false 会得到 disable。preferred 模式还有明文重试；required 并不在所有情况下校验服务器身份，当前解析也没有 verify-full 分支。

证据：internal/db/ssl_mode.go:37、84；internal/db/postgres_impl.go:135。已核对现有代码。网络中间人或被劫持的目标可影响认证流量，无需全面控制本机。是否直接泄漏明文密码取决于协议和服务端认证协商，不能一概断言。[PostgreSQL 官方 TLS 模式说明](https://www.postgresql.org/docs/current/libpq-ssl.html)

缺口：方案已经要求表达协议安全能力，但没有规定自动测试前应满足什么传输/身份条件。“连接通过”不能自动解释为“连接安全”。

保持策略的处理建议：逐数据库明确自动测试安全条件与兼容行为，不静默降级；保存及既定测试时机不必改变。建议尚未采纳。

验证：受控服务器拒绝 TLS、返回错误 CA/主机名证书、采用不同认证机制，观察实际发送与结果措辞。

### R02. 未知字段不能默认当普通内容展示

位置：技术方案 167、169、191、225—229 行。

场景：历史记录引用应用侧官方修订 A；升级、降级、应用配置重建或目录不完整导致该修订不可识别。方案允许尽量只读展示原始内容，而秘密属性依赖应用侧定义。若通用回退把未知值当普通值，旧 Key 可直接进入详情、差异或搜索结果。

证据：文档同时规定定义外置、原始内容回退与秘密按需返回，却没有明确未知字段的分类失败规则。只读限制写入，不自动保证遮蔽。两个子 agent 独立识别同一缺口；尚无实现泄漏证据。

保持策略的处理建议：未知字段默认遮蔽或仅显示其存在，不能借新定义解释旧秘密。不要求把官方模板复制到每本。建议尚未采纳。

验证：删除一个历史官方修订，再测试列表、详情、历史 diff、搜索、复制和恢复，检查返回 DTO 而非仅看 UI 遮罩。

### R03. 单连接池不能提供跨进程生命周期互斥

位置：技术方案 93、302、306 行。

场景：两个 GoNavi 实例打开同一本；A 持有连接，B 迁移替换文件或删除文件/密钥。A 可能继续使用旧连接，在 POSIX 系统还可继续访问旧 inode，造成文件/WAL 错配或成功写入无法再找到。

证据：main.go:86、142 的单实例保护只覆盖 Windows MSI；MaxOpenConns=1 仅是单进程限制。SQLite 官方明确警告使用中的文件被 unlink/rename 的风险。仓库 saved_connections_store.go:33、40 已有跨进程文件锁经验。[SQLite 官方说明 §2.5](https://www.sqlite.org/howtocorrupt.html)

文档虽要求“停止其他写入”，没有给出跨进程的占用和排他资格契约。两个子 agent 独立识别；不把普通 SQLite 合法并发写入等同于必然损坏，风险在文件生命周期操作。

保持策略的处理建议：为每本定义跨进程占用，迁移和删除取得排他资格；不必改变整个应用的多实例政策。建议尚未采纳。

验证：两进程打开、编辑、迁移、删除，以及占用进程被杀、不同应用版本并存。

## 4. 中优先级问题

### R04. 全局事件是 RPC 以外的通道

位置：技术方案 60、62、270 行。

证据：main.go:299；internal/nativewindow/manager.go:150、204。App/AI 的生命周期 emitter 会把一般后端事件送到主窗口和子窗口 SSE，AI run 事件另有专门路由。

条件：密码本独立绑定仍沿用该 emitter，且事件包含本名称、目标地址、验证详情或 DTO。即使子窗口不能调用密码本方法，它也可能收到数据。现有通道已证实，密码本是否误用尚未实现。

建议与验证：采用主窗口专属事件或主动查询；用受控子窗口 SSE 收集器覆盖新增、测试、锁定、错误和刷新。该建议不改变独立绑定策略，未采纳。

### R05. WAL 提交不等于临时容器已经可安全发布

位置：技术方案 130、132、302、304 行。

场景：临时数据库最新内容尚在 WAL，只重命名主文件；或文件/目录/入口登记尚未持久化就返回成功，随后断电。synchronous=FULL 不替代应用层文件发布与登记协议。

建议：明确发布前的关闭/检查点或完整容器发布方式，以及文件、目录和登记同步与恢复顺序。已有禁止复制活跃主库的约束方向正确，但发布也需同等细化。[SQLite WAL](https://www.sqlite.org/wal.html)、[SQLite 原子提交](https://www.sqlite.org/atomiccommit.html)

验证：对密钥写入、库提交、发布、登记及替换各阶段注入中断，检查已返回成功的本可重开，未成功状态不会误删唯一密钥。

### R06. 回退副本没有清理和误恢复边界

位置：技术方案 215、302、306 行。

场景：升级生成完整加密回退副本；之后用户删除记录，旧副本仍包含内容。若受管副本无限保留或普通启动错误回退，会增加磁盘占用或重新引入旧记录。

这属于应用主动管理的完整副本，不同于已经接受的 SSD 取证残留。原方案不承诺清除所有旧副本，本发现不直接宣称违反删除保证；缺少的是可向用户解释的受管副本生命周期。

建议：明确归属、数量/期限、稳定后清理、整本删除覆盖范围和回退触发条件。验证迁移成功/失败/重启及删除后的全部受管文件。未采纳建议。

### R07. 空闲自动锁定遇到草稿的行为未规定

位置：技术方案 154、158、160 行。

场景：用户粘贴一次性 Key 未保存，离开十分钟但未系统锁屏。手动锁定有保存提示，系统锁屏有内存草稿保留；空闲自动锁定未指定采用哪条。等待确认可能阻止自动锁定，直接清空可能丢失 Key。

建议：单独明确空闲分支、草稿保留时间与重新解锁资格；不自动保存、不用确认框阻塞自动遮蔽。短期内存草稿风险已经被接受，本发现不要求改为额外密码或持久化草稿。

验证：编辑中空闲、锁屏、恢复、退出和迟到响应。

### R08. 调试态存在浏览器/WebSocket 入口

位置：技术方案 54、60 行。

证据：当前 Wails v2.15.0 internal/frontend/devserver/devserver.go:34、61、101、207；/wails/ipc 走绑定 dispatcher，CheckOrigin 恒 true。该事实来自本地依赖源码。[Wails 官方 CLI](https://v2.wails.io/docs/reference/cli/)

条件：开发者把真实密码本/凭据用于 wails dev，并注册同一服务。网络调试入口可能调用新增绑定；具体外部网页攻击还受浏览器本地网络策略等条件影响，待实测。

此问题仅针对调试态，不推翻发行构建的原生桥接结论。建议界定开发与发行保障，隔离测试命名空间/数据或真实本解锁条件；尚未选定动作。验证模拟数据在 dev 和发行构建中的入口差异。

### R09. 自定义结构需要独立的并发版本条件

位置：技术方案 175、186、197 行。

场景：两个类型编辑页面基于同一旧结构保存不同修改；仅检查记录 expected_revision_id 不能阻止类型结构覆盖。字段使用检查如果与提交分离，也可能和新增记录交错。

建议：类型修改携带预期 schema_revision，使用检查与提交在同一受控写操作中完成，明确“使用”包括历史。单连接/串行化已有帮助，但仍应规定过期编辑提交的冲突行为。

验证：并发两份类型编辑、新增记录与字段删除、字段仅在历史出现的情况。尚无实现竞态证据，建议未采纳。

### R10. 短期操作标识的重试范围未定义

位置：技术方案 203、268 行。

场景：创建已提交但成功响应丢失或进程中断，随后重试同一提交；若标识只存在内存，重启后不能识别此前结果，可能重复创建或触发另一记录的首次测试。

建议：明确“同一操作”的标识生命周期、是否跨重启持久化、重复结果返回及自动尝试资格。区分最多一次主动尝试与无法仅凭客户端保证的外部请求恰好执行一次。并非所有重启后的新建都应被视为重复操作。

验证：提交/回包/请求开始前后中断后重试，检查约定范围内无重复创建和自动补发。未采纳建议。

## 5. 后续格式兼容提醒

### R11. 读取 crypto_profile 前需要选择格式

位置：技术方案 95、183、300 行。

加密参数需在首次读取前设置，但 book_meta.crypto_profile 也位于加密内容中。首版固定格式可行；未来格式变更时，需要受限探测顺序或非秘密定位提示，不能误报坏库、更不能自动创建覆盖。[SQLCipher 官方 API](https://www.zetetic.net/sqlcipher/sqlcipher-api/)

主 agent 将此项从子 agent 的中优先级调整为低/后续：当前没有要求支持多个既有格式，因此不阻断首版。本轮不新增格式头或改变存储策略。

## 6. 已承认但须实测的发布门槛

### G01. Windows ARM64 和无 CGO 产物

方案 360、365、382 行已经列为待实测，不能当新漏洞。

现有 CI 的 Windows ARM64 在桌面矩阵中，但 .github/workflows/dev-build.yml:678、690 的 C 工具链只针对 windows/amd64；431 行另有 CGO_ENABLED=0 辅助构建。现有配置未证明具备 SQLCipher ARM64 目标工具链。跨编译 CGO 需目标 C 编译器。[Go 官方 CGO 文档](https://pkg.go.dev/cmd/cgo)

验证最终绑定、目标 ABI、密码库链接及安装运行，并验证非密码本 CLI/headless 依赖隔离。没有证据证明 ARM64 做不到，也不能按目前构建脚本直接承诺完成。

### G02. 内嵌 SQLite 的 WAL-reset 修复

方案 91、105、365 行已经要求锁定依赖。本轮发现可以具体化该门槛：SQLCipher 4.14.0 官方说明包含 SQLite 3.51.3 的 WAL-reset 修复，旧内核在特定多连接并发/检查点条件下可能损坏数据。[SQLCipher 官方发布说明](https://github.com/sqlcipher/sqlcipher/releases/tag/v4.14.0)、[SQLite WAL-reset 说明](https://www.sqlite.org/wal.html)

当前方案没有选定依赖，因此不能声称已经引入该缺陷。必须核实实际 SQLCipher/SQLite 版本及回补补丁，不能仅凭 Go 包名或单进程连接数推断安全。此建议不要求改变 WAL 或 SQLCipher 策略。

## 7. 已接受边界与已有控制

本轮没有将以下事项重新计作漏洞：全面系统/账户入侵；剪贴板历史及他方已读取内容无法撤回；无用户备份导致密钥遗失不可恢复；锁屏草稿保留短期内存；磁盘取证残留；完整旧合法文件回滚。

已有明确控制包括：拒绝明文降级、禁止 dailysecret 保管密钥、独立密钥命名空间、原始密钥契约、临时文件禁止、密钥不进 DSN、秘密按需读取、跨源重定向限制、响应及错误脱敏、SSH身份核验、取消与旧会话结果隔离。

Gemini URL Key、默认 HTTP 重定向、SSH 地址/用户名日志、上下文缺失和剪贴板条件清理等复用风险，在原方案已被承认。本轮保留为工程测试点，不重复算新增发现，也不把安全控制声明等同于已经实现。

## 9. 讨论后的复核结论与下一步验证范围

用户要求主 agent 判断审查发现是否真实、是否值得处理，避免把假设风险扩大为首版功能。本节记录讨论后的取舍，不修改两份源文档，也不改变 SQLCipher、系统保管密钥、本地存储、原生桌面访问等既定策略。

| 项目 | 复核结论与首版处理范围 |
| --- | --- |
| R01 网络验证 | 值得验证已保存目标、用户选择的安全配置和无静默降级；连接成功不等于传输安全。不能由此要求所有内网数据库强制 TLS，或扩大为全驱动安全改造。 |
| R02 旧字段定义 | 移出高优先级风险。内置字段 ID 与秘密分类保持稳定，保留历史定义已是原策略；未知字段默认遮蔽作为简单兜底即可，不引入定义恢复框架。 |
| R03 迁移与删除 | “迁移”指未来内部存储格式升级，不是设备迁移。首版固定格式，平台预设更新通常不需要修改用户库结构；仅预留格式版本。删除整本时处理其他进程占用值得做，可采用简单文件锁或占用检查，不引入复杂租约系统。记录删除按正常事务处理。 |
| R04 事件路径 | 值得处理，落实主窗口专属事件或主动查询，属于小范围入口约束。 |
| R05 创建与持久化 | 可靠写入、完整历史、失败不发布半成品需要实测；未来替换/升级文件的完整框架暂缓。 |
| R06 回退副本 | 依赖未来真实升级场景，首版不建设内部迁移回退副本及管理功能。 |
| R07 自动锁定草稿 | 值得明确，复用系统锁定的即时遮蔽和短期内存草稿行为；不能因为未保存内容阻止自动锁定，也不持久化明文草稿。 |
| R08 调试态 | 开发验证仅使用合成凭据，确认发行态入口边界；不扩大为整套调试安全系统。 |
| R09 自定义结构并发 | 采用常规预期结构版本校验及受控写入即可，不建设复杂版本管理框架。 |

下一步是最小技术可行性验证，而非正式产品实现：

1. 调研并选择 Go SQLCipher 绑定，核对维护情况、实际内核版本、许可证和目标平台构建条件。
2. 使用合成数据验证真实加密、正确/错误/缺失密钥、系统密钥保管跨进程读取，以及失败时不降级、不覆盖旧密钥。
3. 验证记录与历史的事务一致性、关闭重开、辅助文件的加密行为和简单跨进程占用约束。
4. 结合现有代码核对原生 Wails 主窗口入口、事件路由及秘密不进入普通持久化、日志和 HTTP/MCP 通道的边界；尚未实现的部分不能报告为已通过。

本轮不实现正式 UI、云端、同步、备份导入导出、设备迁移或完整内部升级框架，不使用真实凭据或发起付费模型请求。验证报告应区分已实测、源码确认、推断和未验证；若发现阻断项，给出证据和最小建议，不擅自改变既定策略。
