# GoNavi PR 提交规范与模板

本文件是 `.claude/ISSUE_WORKFLOW.md` 的配套：Issue 处理完成后，按本文组织 PR。

**标题和正文一律使用中文。** 提交信息规范见 `ISSUE_WORKFLOW.md` 三。

---

## 一、PR 基本信息

| 项目 | 要求 |
| --- | --- |
| base 分支 | `Syngnat/GoNavi:dev`（禁止直接指向 `main`） |
| head 分支 | 个人 Fork 的 `fix/*` 或 `feature/*` |
| 标题语言 | 中文 |
| 正文语言 | 中文 |
| 范围 | 一个 PR 只解决一类问题 |

标题格式：

```text
emoji type(scope): 中文描述
```

示例：

```text
🐛 fix(query-editor): 修复 CTE SQL 被误判为高风险
✨ feat(data-sync): 调度清单支持启停与立即运行
```

禁止：英文标题、机器生成的泛化标题、与改动不符的描述、无关的 Issue 编号。

---

## 二、PR 正文模板

复制以下模板填写。**只写实际做过的事**；未执行的验证不得写成已通过。

```markdown
## 背景与问题

<关联 Issue： #编号>

<用 1-3 句说明原有行为、用户可见现象、为什么需要改。>

## 根因

<定位到具体模块与文件，说明问题为什么发生。既有问题与本 PR 是否处理要写清楚。>

## 变更点

- <改动一>
- <改动二>
- <补充的测试>

## 影响范围

- <受影响的模块、接口、界面或数据路径>
- <不涉及的部分也明确写出，例如：不涉及后端接口、数据库数据或存储格式变更>

## 验证方式

- `<实际执行的定向测试命令>`
  - <结果，例如： N 个测试文件通过， M 项测试通过>
- <实际执行的人工验证步骤与结果>
- <如执行过构建： 平台与命令>

## 风险与回滚

- <风险点；无风险时写明「无数据或接口兼容性风险」>
- 如需回滚，撤销本 PR 的提交即可，<说明是否涉及数据迁移或配置变更>

Closes #<编号>
```

填写要求：

- 「验证方式」必须与 `git log`、实际终端输出一致，可被维护者复核。
- UI 或交互改动附修复前后截图或录屏。
- 涉及兼容性、数据变更或构建链路时，风险与回滚段不得省略。
- 正文使用真实 Markdown 段落与列表，不要出现字面量 `\n`、`\t`。

---

## 三、创建方式

中文正文优先写入 UTF-8 文件后用文件方式提交，避免转义问题：

```powershell
# 1. 写正文（UTF-8 无 BOM）
$body = Get-Content .claude\tasks\<任务目录>\pr.md -Raw -Encoding UTF8

# 2. 确认文件为真实换行的 Markdown
Get-Content .claude\tasks\<任务目录>\pr.md -TotalCount 20

# 3. 创建 PR（由用户授权后执行）
gh pr create --repo Syngnat/GoNavi --base dev --head <fork>:<branch> --title "<中文标题>" --body-file .claude\tasks\<任务目录>\pr.md
```

注意：PowerShell 双引号字符串不会把 `\n` 转成换行，因此不要把整段正文直接写在命令行参数里。

## 四、提交前检查

```powershell
git fetch upstream --prune
git log --oneline upstream/dev..HEAD
git diff --name-only upstream/dev...HEAD
git status --short
```

逐项确认：

- 已基于最新 `upstream/dev`，必要时先同步再重测。
- 改动文件清单里**没有**个人辅助内容：
  - `AGENTS.md`、`CLAUDE.md`、`.claude/`、`.agents/`
  - issue 扫描记录、任务草稿、环境记录、会话摘要、PR 草稿
- 没有密钥、连接串、隐私数据、调试输出、临时文件。
- 没有与本次 Issue 无关的格式化或重构。
- 提交信息为中文，且与 PR 标题一致。

> 本地 `dev` 允许承载个人工具提交，**绝不能**作为 PR 的来源分支。发现 PR 分支包含了个人内容时，停止创建 PR 并先清理分支。

---

## 五、UI 改动的额外要求

- 创建 PR 前启动可供用户访问的应用或浏览器预览，并交给用户人工测试。
- 自动化测试、构建成功或历史测试记录**不能替代**这一步。
- PR 正文附修复前后对比。

---

## 六、授权与回读

1. **必须等用户在当前需求中明确说「可以提交 PR」或给出等价授权。**
   「测试通过」「审查通过」只表示验证完成，不代表允许推送或创建 PR。
2. 创建 PR 属于外部写操作，未获授权不得执行 `git push`、`gh pr create` 或更新 PR。
3. 创建或更新 PR 后必须回读并核对：
   - 标题、正文（中文、实际分段）
   - 源分支与 base 分支
   - 提交数与文件列表
   - Issue 关联是否为 `Closes #编号`
4. 本地命令显示成功不能替代回读。发现不一致时先修正远端并再次回读，再通知用户或请求评审。

---

## 七、PR 创建后的收尾

- 向用户汇报 PR 链接、标题、base 分支、文件范围与验证摘要。
- 列出 `ISSUE_WORKFLOW.md` 五中 B 类遗留项，说明是否需要另开 Issue。
- 维护者要求修改时，按「一处修改一次提交」处理，并遵守 `ISSUE_WORKFLOW.md` 四至六的审查流程。
- 需要更新 PR 正文时，重新按本文模板核对，不要只改标题。
